# 方針委譲方式の比較実験

## 仮説

Cursorが調査・編集・テストを逐次実行する代わりに、Strataの事前調査を受けて一度だけ「解決方針・制約・再相談条件・深度」を判断すると、同じ複数ファイルの作業でCursor総トークンを減らせる。ただし品質は維持する。これは仮説であり、達成保証ではない。

## 参考にした設計

[Maestro](https://github.com/ndouwesalvador/maestro)の例外時の監督、[Aider Architect/Editor](https://aider.chat/2024/09/26/architect.html)の解法と編集の分離、[Anthropic Code Execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)の中間データを会話へ流さない構成、[Serena](https://oraios.github.io/serena/01-about/035_tools.html)の必要情報だけの取得を参考にしています。それぞれの公開削減率を本実験の達成率として使いません。

## 実行前に固定した条件

- fixture：`tests/fixtures/catalog_policy/`。カタログAPIのquery.py、pagination.py、service.pyの関連不具合を一つの依頼で修正。
- 作業：正の整数クエリ検証、1始まりのページ分割、activeで絞ってからソート・ページ分割、正しいtotalとhas_next、入力を変更しないこと。公開関数のシグネチャ・返却キーを維持。
- 品質：固定15テスト（パラメーター化した追加ケースを含む）、許可された3ファイルだけの変更、Strata方式は独立レビューと適用も成功すること。
- 両条件は同じGit treeから開始。Cursor単独側にも全作業を一括で渡す。複数回の単独実行を足し合わせて分母を増やさない。
- Cursor CLI 2026.10.01-e373342、同じcomposer-2.5、新規セッション。キャッシュ読込・書込を含むreported usageの4項目を合算。
- 初回は1対応ペアの機能・費用確認。統計的な有意差や一般的削減率は主張しない。
- Supervisorは最大1回。未解決なら停止して失敗として記録する。ローカルWorkerは1フェーズ8ステップ以内で読取り・編集・登録テストを実施できる。
- 深度はCursorがlow/medium/highから選択。実行側は同じ深度で編集と独立レビューを行う。

Strata APIのモデル一覧は`qwen3.8-flash-next-iq3_s`を返しました。推論深度の対応設定はunverifiedであり、low/medium/highを送信したことは、その推論強度がサーバーで実際に制御された証明ではありません。

## 方式

1. 同一fixtureの二つのrepoで、初期テストが失敗することを記録。
2. Cursor単独で全依頼を実行し、独立に最終テスト・変更範囲・使用量を確認。
3. Strataがコードとテストを調査。背景・目的・現状・要求を1,100文字以内の資料にし、具体的な原因と修正案を記載。全文はローカルに保存。
4. Cursorは資料・受け入れ条件・編集範囲から短い方針JSONを返す。ツールやコード閲覧は使用しない。
5. Strataが方針を受け、一つのworktreeで3ファイルを修正・テスト。別コンテキストで全文差分をレビューし、許可範囲で適用。
6. 適用先でも15テストを実施し、Cursor単独との総トークン比と品質を評価。

情報経路の修正として、Workerの最終回答全文をresponse_idで保存しました。状態表示は1,500文字のまま、機械判定だけが全文証拠を取得し、ハッシュと上限を確認します。上限を超える回答を黙って切りません。これは前回見つかった失敗の前提修正で、Cursor削減率そのものとは別です。

## 再現方法

Strataと共有コーディネーターを起動し、queued接続用configと認証を用意します。configのunitテスト設定は固定fixture用に上書きされます。出力先は新規ディレクトリにしてください。

```sh
python3 tools/evaluate_policy.py --out /absolute/private/policy-eval-01 --config /absolute/private/config.json --cli /absolute/path/to/cursor-agent --model composer-2.5
```

report.jsonに初期tree、fixtureと主要実装のSHA-256、呼出しごとの使用量、資料と方針、最終テスト・変更範囲・終了状態を保存します。失敗もreportに記録するため、CLIの終了コードだけで合格判定しないでください。生ログにはローカルパス等があり、そのまま公開しません。

## 適用範囲

これは実験用CLIです。Cursor拡張の既定動作は切り替えていません。任意数の依頼の統合、例外の再相談と再開、並列実装の統合を完成させた実験ではありません。今回の「修正ループ」は一つのWorkerの8ステップ内であり、独立レビュー拒否後の自動再実装は行いません。

## 試行中の設定変更と失敗（削除せず記録）

第1試行は事前固定条件どおり。Cursor単独は91,015トークン、15テスト成功。Strataは調査の4ステップ目でCoordinator operation failedとなり停止しました。詳細な上流原因は既存エラー表示から断定できません。監督Cursorは未呼出しで、新方式の比較は未完了です。調査出力予算2,048、上流待ち90秒でした。

第2試行は調査出力予算を1,024へ変更し、同じ課題を両方式とも新規実行しました。Cursor単独は87,248トークン、15テスト成功。Strata調査はfinish_reason=lengthによる出力打切りで停止。監督Cursorは未呼出しです。短い出力予算による調査の不安定化を確認しました。

推論APIのhealthとslotsを確認し、処理中要求がないことを確認してから各再試行を開始しました。失敗したタスクを同じIDで自動再実行していません。

第3試行は調査出力予算2,048、上流待ち180秒、要約生成指示700文字（検証上限1,100文字）へ変更しました。これは事前登録条件のままの反復ではなく、失敗を受けた調整です。今回の実験は最大3試行で区切ります。最も良かった結果だけを抜き出しません。

上流待ちはコーディネーターの`--request-timeout 180`で再現できます。既定値は90秒のままで、既存の常駐サービスを自動再起動する変更ではありません。

## 結果

第3試行も、事前調査の4ステップ目でモデル出力が打ち切られ、needs_supervisorとなって停止しました。上流待ち時間を延ばしたことで出力上限まで応答を受け取れましたが、所定の調査結果は完成しませんでした。2,048という生成予算と短いJSONの指示だけで、調査と回答を安定させられることは確認できません。

- Cursor単独：第1試行91,015、第2試行87,248、第3試行87,332トークン。各15テスト成功、変更はquery.py・pagination.py・service.pyの3ファイルのみ。
- 方針委譲方式：3試行とも事前調査で停止。監督Cursor呼出し0回。実装・レビュー・適用には未到達。
- **品質ゲート：不合格。比較比率：算出不可。Step 1：達成せず。** Cursorを呼べなかったことを「100%削減」として扱わない。
- 今回の全試行で実際に報告されたCursor使用量は**265,595トークン**。すべて比較対照のCursor単独実行分であり、開発実験の支出として残す。
- Strata側は第1試行で報告済みprompt 3,672／completion 214、第2試行6,310／1,234、第3試行6,276／2,246。第1試行の失敗した推論要求は使用量不明であり、その消費をゼロと断定しない。

[機械可読の全結果](policy-experiment-results.json)には各試行の使用量内訳、初期tree、ソースハッシュ、終了状態、独立テスト件数を保存しています。成功した条件だけを選んだ集計ではありません。一時コーディネーターとSSHトンネルは各試行後に停止しました。

## 結論と次に必要な検証

**今回の結果では、方針委譲というアーキテクチャの効果を判定できません。** 監督Cursorを使う前のStrata調査・構造化出力が実験のボトルネックでした。Cursorの入出力の圧縮効果や、方針を一度決めれば十分かどうかを検証できた結果ではありません。

一方で、固定した課題をCursor単独で解けることと、初期コード・テストが比較に使用できることは確認できました。74件の機能テストが成功していても、実モデルとの統合成功を保証しないことも再確認しました。

実験手順には改善が必要です。今回のrunnerはCursor単独を先に実行したため、Strataの事前調査失敗を繰り返す間にも比較用Cursorトークンを消費しました。次回は以下の順序にします。

1. Cursorを呼ばず、固定fixtureでStrata調査だけの再現試験を行う。
2. 推論深度・思考出力・構造化出力について、利用中サーバーが実際に対応している設定を確認する。未対応のパラメーターを送っただけで制御できたと扱わない。
3. 中間の取得結果はプログラムで保持し、調査と短い報告の生成を分離する案を単独検証する。生成打切り・形式違反をCursorへの再相談理由にしない。
4. 調査→方針→実装→テスト→レビュー→適用が安定してから、同じ固定課題・同じモデルで対応する比較を行う。条件を変えていない比較対照を再利用する場合は、その旨と測定時点を明示する。

この時点で本方式をCursor拡張の既定動作には採用していません。追加の試行は行わず、既存の79.85%削減のチェックポイントを保持します。
