- 3課題：ページ分割、区間統合、有効期限付きキャッシュ。各条件2回。1回目は単独→併用、2回目は併用→単独。Agentを同時には実行しない。

- 明示した委譲プロンプトで運用。IDE拡張／Chat画面やSkill自動読込みの検証ではない。
- 1実行300秒の上限。最大2委譲・合計30stepsを指示。温度等のCursor非公開設定やキャッシュは固定・消去していない。

## 計測手法

CLIのstream-json末尾にあるresult.usageを使用した。表示文章の文字数から推定していない。入力＋出力＋キャッシュ読込＋キャッシュ書込を総量とし、reasoningを追加加算しない。[Cursor公式TokenUsage定義](https://cursor.com/docs/sdk/typescript)に従う。CLIの実装もセッション内で使用量を累積していることを確認した。料金明細は取得しておらず、トークン増加率を請求額増加率と解釈しない。

## 結果の解釈

今回の単独課題は数行〜十数行の修正であり、Cursor自身の調査・修正は短く済む。一方、併用はMCPツール取得、契約作成、状態取得、差分・テスト証拠取得、適用確認を必要とする。実行ログのツール回数はJSONへ記録した。この追加のやり取りが増加に寄与したと考えられるが、各ツール別の厳密なトークン内訳は取得していない。
改善候補は、小さな既知の修正をCursor側で完結させる委譲判断、完了結果・差分・テスト証拠のまとめ取得、待機中のモデル往復削減である。変更後は同じ条件で再測定する必要がある。大規模コード調査で削減できるかは今回の結果からは判断できない。

## 再現方法と証拠

[準備・実行・集計コマンド](evaluation.md#実行と集計)とtools/prepare_token_evaluation.pyを使用する。実行順・課題・初期コードは準備スクリプトに固定している。実行前にCursor CLIへログインし、同じモデル名、Strataとコーディネーターを準備する。
[機械可読の実測値](token-evaluation-results.json)に各実行の4種トークン、正解判定、tool呼出回数、Strata側usageと深度を保存した。Strata usageをCursorに加算していない。生ログはローカルに保持し、公開資料から利用者の絶対パス・認証情報・セッションIDを除いている。

## 限界

3課題×2回の小規模な予備評価で、統計的な一般化はできない。モデル出力とキャッシュは変動する。実行順は反転したがキャッシュ状態を完全には統制していない。設定したassert以外の欠陥や実プロジェクトでの成功率、複数Agent並列時の削減率、Cursor IDEの実動作は未評価。今回のトークン総量はキャッシュを含む処理量で、金銭コストやコンテキスト窓の大きさではない。
使用量取得確認の「OK」だけの予備実行は両条件の課題とは別なので比較から除いた。評価中断後、一時コーディネーターとSSHトンネルを停止した。中断した実行のusageが未確定のため、記載の総量は完了済み比較ペアに限る。新設計の1/100達成を示す結果ではない。

現在の合格目標は単独実行の1%以下（1/100以下）。完了済み5組の単独総量395,574に対する目標上限は3,955トークン（整数で切捨て）で、旧構成834,455は不合格。実測値は変更せず、合格目標だけを更新した。
